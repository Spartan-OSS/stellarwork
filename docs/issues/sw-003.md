# SW-003: Verify atomic rollback and isolation for SAC transfer failures

Status: **Blocked**  
Proposed Drips complexity: **High** (organizer/maintainer review required)  
Dependencies: SW-001  
Starting paths: `contracts/escrow/src/test.rs`

## Problem

Python rollback is modeled; it does not verify host transaction rollback or SAC restrictions.

## In scope

- Force funding failure from insufficient token balance; assert no Funded state/liability/event persists.
- Create a deterministic token-transfer failure during approval and during the second split transfer; use SAC authorization restrictions where supported, or a clearly scoped failure-token test double.
- Inspect client/worker/contract balances, aggregate liability, milestone status, and event persistence after rejection.
- Fund two engagements and settle only one; assert the other remains untouched.

## Acceptance criteria

- A failed second split transfer reverts the first transfer and all state.
- Duplicate funding/approval/refund/resolution cannot move tokens twice.
- Full refund and full payout split endpoints pass and never transfer a negative amount.

## Excluded work

No arbitrary production tokens, reentrancy policy changes, rescue withdrawal, or frontend work.
