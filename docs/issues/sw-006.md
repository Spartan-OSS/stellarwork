# SW-006: Prove three-party wallet authorization on testnet in a small harness

Status: **Blocked**  
Proposed Drips complexity: **High** (organizer/maintainer review required)  
Dependencies: SW-001, SW-002, SW-003, SW-004; G3 deployment metadata  
Starting paths: `integration/consent-harness/ (new); docs/consent-flow.md`

## Problem

create_engagement requires client, worker, and arbitrator on the same parameters; a normal single-wallet transaction is insufficient.

## In scope

- Build a minimal TypeScript harness around the verified contract and generated bindings.
- Demonstrate sequential collection of all required authorizations without collecting wallet secrets.
- Bind network passphrase, contract, terms, deadlines, and auth expiry to the request; reject mutated and expired authorization entries.
- Use test accounts to confirm the stored roles and milestones after ledger inclusion.

## Acceptance criteria

- Three distinct testnet accounts authorize identical terms and create one engagement.
- Missing signature, changed terms, wrong network, and expired authorization are rejected.
- Instructions reproduce the flow and separate simulation, signature collection, submission, and confirmed inclusion.
- A reviewer confirms the chosen wallet supports the required auth signing; failures are reported as blockers.

## Excluded work

No polished Next.js app, production wallet release, custody service, or weakening consent to bypass integration problems.

## Verification

Document exact npm install/test/run commands; commit dependency lockfile and mock tests plus a redacted testnet receipt.
